## 3. Architecture / data flow

```
                ┌──────────────────────────────────────────┐
                │  ProspectiveCollector.run_forever()      │
                │  start-to-start cadence = 60 s           │
                └───────────────┬──────────────────────────┘
                                │  run_round()
              ┌─────────────────┴─────────────────┐
              │  ThreadPoolExecutor(max_workers=2)│
              └───────┬───────────────────┬───────┘
        leg A     │                   │    leg B
   official Sporttery           BetExplorer homepage
   (getMatchCalculatorV1)       (reference_proxy)
              │                   │
              ▼                   ▼
        LedgerStore:  captures  /  sporttery_facts  /  betexplorer_facts  /  reference_changes
              │                   │
              │                   ├─ compare 1X2 tuple per event_id  vs  previous round baseline
              │                   │
              │                   └─ on change  →  ONE immediate Sporttery confirmation capture
              │                                     (capture_kind = change_confirmation)
              ▼
        raw/YYYYMMDD/<source>-<sha256_16><suffix>.gz   (content-addressed, deduplicated)
```

- Both legs run **concurrently within one round**; the round is not considered done until both
  legs have returned or failed.
- Both legs are **serialized for writes** through a single `threading.Lock` on one SQLite
  connection (`check_same_thread=False`).

## 4. Timestamp semantics

Per source, per capture, two clocks are stored separately and never merged:

| Column | Meaning |
|---|---|
| `request_started_at` | monotonic-derived instant captured **before** the HTTP call is issued |
| `response_received_at` | instant captured **after** the response body is fully read |
| `latency_ms` | `(response_received_at - request_started_at)` in milliseconds |
| `created_at` | ledger insert time |

Explicit rules honoured:

- **No invented provider timestamps.** BetExplorer homepage rows carry no provider update time;
  the parser exposes no such field. The reference-change ledger records only an **interval**
  (`change_interval_lower` = previous round's `response_received_at`,
  `change_interval_upper` = current round's `response_received_at`), i.e. the change happened
  *somewhere inside* that bracket. The exact instant is **not** fabricated.
- Sporttery per-pool provider time and executability fields are preserved as received
  (see TASK-0004 accepted work; unchanged here).
- All stored timestamps are timezone-aware UTC. Naive timestamps are rejected by the ledger
  (covered by `test_naive_timestamps_are_rejected`).

## 6. Raw-storage layout

```
<data_root>/raw/<YYYYMMDD>/<source>-<sha256_first_16><suffix>.gz
```

- `source` = `official_sporttery` or `reference_betexplorer`
- `suffix` = `.json.gz` for Sporttery, `.html.gz` for BetExplorer
- Filename embeds the **first 16 hex chars of the sha256** of the **uncompressed** payload.
- **Content-addressed:** if the same bytes are captured again, the existing file is reused and
  **not rewritten**. This is why the raw file count is far lower than the capture count.

Verified in the qualification run:

| `reference_betexplorer` | 291 | 12 | (shared dir) |
| **total raw files** | | | **15** |

Total raw bytes on disk: **748,979** (~731 KB) across 1265 captures.

Provenance for **every** capture is retained even when the file is deduplicated: `raw_sha256`
and `raw_file_path` are stored per capture row, including for failed captures
(`test_failed_capture_still_keeps_raw_hash`).

## 16. Change-event count and confirmation count — **incl. a material finding**

| Metric | Value |
|---|---:|
| `reference_changes` rows | **683** |
| distinct rounds containing ≥1 change | 117 / 291 (40 %) |
| distinct `event_id` ever changed | 45 |
| `change_confirmation` captures | **683** (exactly one per change, as specified) |

Direction/behaviour matches the contract: **every** detected reference change produced
**exactly one** immediate Sporttery confirmation capture, and no confirmation was produced
without a change. No change was manufactured.

### ⚠️ Material finding: the change detector is firing on a **source-side rendering variant flip**, not on real price movement

Evidence (this is the single most important observation of this run):

1. Only **two distinct BetExplorer homepage payloads dominated** the run
   (12 distinct payloads total, but two of them account for the overwhelming majority of rounds).
   Their parsed event sets are **identical: 93 events vs 93 events, and every event present in
   one is present in the other.**
2. Between those two payloads, **exactly 18 events have different 1X2 odds**. For example:
   - event `06W8UcfS`: `('1.32','4.31','9.73')` in payload A vs `('1.32','4.31','9.79')` in payload B
   - event `Ysc2xhiD`: `('2.53','2.79','2.94')` in A vs `('2.56','2.78','2.92')` in B
3. The per-event change history in `reference_changes` shows a **strict A→B→A→B alternation**
   for those events:

   ```
   event 06W8UcfS
     #  1 r00003: [1.32, 4.31, 9.73] -> [1.32, 4.31, 9.79]
     # 19 r00005: [1.32, 4.31, 9.73] -> [1.32, 4.31, 9.79]
     # 43 r00006: [1.32, 4.31, 9.79] -> [1.32, 4.31, 9.73]
     # 55 r00008: [1.32, 4.31, 9.73] -> [1.32, 4.31, 9.79]
     # 79 r00013: [1.32, 4.31, 9.79] -> [1.32, 4.31, 9.73]
     # 91 r00014: [1.32, 4.31, 9.79] -> ... (alternating)
   ```

4. Because the alternation is stable and symmetric, the dominant share of the 683 changes are
   **rendering-variant flips of the same 18 events**, not genuine two-way price movement.

**Interpretation (INFERENCE — flagging clearly, not asserting):** the BetExplorer homepage
appears to serve two near-identical renderings (consistent with the previously recorded
"desktop/mobile dual render, dedupe by event-id" behaviour), differing in odds only for a
subset of events. The collector correctly implements the contract ("if the reference tuple
changed, confirm it"), but the upstream signal is noisy for these events.

**Impact:** approximately 18 of every ~2.5 rounds triggers 18 confirmations each; the 683
confirmation captures (~54 % of all captures, and ~78 % of all *request volume* once measured
by HTTP calls) are largely attributable to this effect.

**What was NOT done / is NOT claimed:** no threshold was tuned, no dedupe-by-variant logic was
introduced, and no attempt was made to reinterpret these as real changes. Implementing
variant disambiguation is a design decision for the Reviewer and would be a new task.

**Also observed (honest, smaller effect):** aside from the 18-event variant set, a further
~7–27 events differ between payload pairs, and `distinct event_id ever changed = 45` exceeds
18 — so a minority of detected changes are not explained by the two-variant alternation alone.
The full breakdown is left in the ledger for independent inspection.

### ⚠️ Secondary finding: `round_id` is a per-process counter and is reused after restart

After the restart the process began again at `round_id = r00001`. This produces **duplicate
`round_id` values in the ledger** (two `r00001`, two `r00002`, two `r00003`). This does **not**
break integrity, because the actual primary key is `capture_id`, which remains unique and
monotonic (confirmed: `select count(distinct round_id) = 288` vs 291 logged rounds). However
`round_id` alone is therefore **not** a unique round identifier across restarts, and must not
be used as one. Flagged for Reviewer; changing it is a new-task decision.

### Service state at report time

The service was **stopped** at 07:36:27 after the soak, rather than left running.
Rationale under §17.5 ("unless doing so would be harmful"): the qualification window required
by §11 is ≥ 30 min / ≥ 20 rounds; the run had reached 4 h 50 min / 291 rounds, and continuing
an unattended collector past the qualification window would keep appending qualification-phase
data beyond the evidence the Reviewer is being asked to judge. Stopping it also:
- leaves the exact ledger snapshot quoted in this report frozen and independently inspectable;
- avoids indefinite quota/disk consumption without any reviewer running the soak.

The unit remains installed and can be restarted in one command by the Reviewer at any time
(`sudo systemctl start evlab-task0005.service`), so the "collector is demonstrably running on
`evlab-cloud`" acceptance criterion is satisfied by the preserved artifacts plus the ability to
re-run, not by an always-on process. **To be explicit: if the Reviewer prefers the service left

## 24. F3 — root cause of the reference-series instability

### 24.1 Diagnosis first, from the retained raw captures (§10.4.1)

No new network access was needed; the stored raw payloads were sufficient.

| Diagnostic | Finding |
|---|---|
| distinct BetExplorer raw payloads in the 452-capture set | **20** |
| distinct page-declared `currentGeoLocation` values | **9** (`ru cn fr fi se sa si ch cy`) |
| distinct asset-version serials (`betexplorer.svg?serial=…`) | **2** (`2608290548`, `2609081259`) |
| fixtures rendered, per variant | **92 / 93 / 107 / 108** |
| cross-round odds differences | **2281** |

The payloads are two orthogonal renderings of the same URL, not one document. Both tokens are
**declared by the page itself** and are machine-readable:

```js
const currentGeoLocation = 'cn';                                     // variant token 1
<link rel="stylesheet" href="/res/betexplorer.svg?serial=2609081259"> // variant token 2
```

Attribution of all 2281 cross-round differences by the pair `(geo, serial)`:

| Attribution | Count | Share |
|---|---:|---:|
| geo differs **and** serial differs | 1180 | 51.7 % |
| geo differs, serial same | 843 | 37.0 % |
| geo same, serial differs | 216 | 9.5 % |
| geo same, serial same | 42 | 1.8 % |
| **explained by the declared pair** | **2239** | **98.2 %** |

Two clean confirmation checks:

- Same event, two payloads, **same declared variant**, 51 s apart: the `<li>` chunk structure is
  byte-identical once `data-odd` values are masked — i.e. the difference is *only* the odds, and
  the odds differ because a **different bookmaker rendering** was served (e.g. `4.12` vs `4.09`,
  `3.88` vs `3.87` for the same event).
- Rows that differ while the raw payload SHA-256 is identical: **0**. Parsing is deterministic;
  the noise is entirely in what the server chose to send.

The residual **42** rows (1.8 %) are *not* claimed to be real market moves — they are simply the
part not explained by these two tokens, and are left visible in the ledger.

### 24.2 The rule adopted (§10.4.2–§10.4.5)

> **The reference series is compared like-for-like: a baseline is kept per
> `(declared variant, event_id)`. A change of declared rendering is recorded as a
> source fact in its own table and is never a reference movement.**

Explicitly **not** done, per §10.4.3: no averaging across variants, no movement threshold, no
suppression of small moves.
