## 4. Phase B — source feasibility

### 4.1 Sporttery official webapi — the primary Sporttery leg

`https://webapi.sporttery.cn/gateway/jc/football/getMatchCalculatorV1.qry`

- Source type: **official** (the market itself; this is the Sporttery leg, not a reference).
- Auth/cost/access: free, unauthenticated, no account, no token. Not a scrape — a public JSON endpoint.
- **Access rule, measured.** The endpoint answers `HTTP 567` with a ~7.35 kB HTML challenge page when the request carries **no `Referer` header**, and `HTTP 200` + JSON when it carries **any** `Referer`. Back-to-back isolation run 2026-09-24 09:16–09:21 (same client, same proxy, same URL):

  | request headers | status | bytes | body |
  |---|---|---|---|
  | UA only | 567 | 7,352 | HTML challenge, 2 markers |
  | UA + `Accept` | 567 | 7,351 | HTML challenge |
  | UA + `Accept` + `Accept-Language` + `Origin` (no Referer) | 567 | 7,351 | HTML challenge |
  | UA + `Referer: https://www.sporttery.cn/` | **200** | **18,044** | JSON `success=true` |
  | UA + `Referer: https://www.lottery.gov.cn/` | **200** | 18,044 | JSON, byte-identical |
  | UA + `Referer: https://webapi.sporttery.cn/` | **200** | 18,044 | JSON, byte-identical |
  | bare URL, no params, no Referer | 567 | 7,352 | HTML challenge |
  | bare URL **with** Referer | **200** | 97,248 | JSON, all pools |

  The determining factor is the presence of `Referer`; its value is irrelevant.
  `Accept` / `Accept-Language` / `Origin` changed nothing. The `/uniform/` gateway is
  an alias — it returns byte-identical payloads and obeys the same rule
  (`uni_…_without_ref` → 567, `uni_…_with_ref` → 200).
- Query parameters are **optional filters**: `poolCode` narrows the payload;
  omitting all parameters returns every pool for every listed match (97,248 B,
  9 matches, pools `crs/had/hafu/hhad/ttg`).
- Timestamp semantics (three distinct clocks, never merged):
  - `observed_at` — ours, second precision, set by the collector.
  - `had|hhad|ttg.updateDate` + `updateTime` — the provider's odds-change stamp for
    that pool (Beijing time, second precision). Observed example: `2026-09-23 18:51:22`.
  - `value.lastUpdateTime` — payload-level provider stamp. Observed: `2026-09-23 21:50:41`.
- Markets/lines: `had` (standard 1X2), `hhad` + `goalLine` (handicap 1X2),
  `ttg` (8 buckets `s0..s7`), `crs`, `hafu`. `poolList` carries per-pool `allUp` /
  `bettingSingle` availability and `poolCloseDate` / `poolCloseTime`.
- Sporttery side retained fields: `matchId`, `matchNumStr`, `taxDateNo`,
  `businessDate`, `matchWeek`, `leagueAbbName` / `leagueCode`, team short + full
  names and ids, `matchDate` + `matchTime` (Beijing), `matchStatus`, `sellStatus`,
  per-pool odds and line, provider update stamps, our `observed_at`, payload SHA-256.
- Historical/index route `getUniformMatchResultV1.qry` also returned **200 JSON** with
  the full parameter set (`resultCount`, `pages`, `leagueList`, `matchResult`), so the
  v1 blocker is gone there too. It was probed for reachability only; **no historical
  backfill was attempted** (the task forbids broadening into backfill work).

### 4.2 500.com mirror — secondary leg, cross-validation

`https://trade.500.com/jczq/?date=<YYYY-MM-DD>`

- Source type: **mirror of Sporttery**. Its `nspf` pool reproduces the official HAD
  prices exactly (§5.3). Label in this report and in code: `sporttery_mirror_500`.
  It is **not** official; `official_update_time` is null for this leg.
- Free, unauthenticated. `playid` switch: `270` TTG, `271` correct score, `272`

- **Retention boundary, measured** (the legacy note said "~30 days"; this is now a
  measured interval, not a guess):

  | requested age | requested date | HTTP | bytes | rows | returned `data-processdate` | verdict |
  |---|---|---|---|---|---|---|
  | 7 d | 2026-09-17 | 200 | 121,863 | 11 | `2026-09-17` | EXACT |
  | 14 d | 2026-09-10 | 200 | 108,289 | 7 | `2026-09-10` | EXACT |
  | 21 d | 2026-09-03 | 200 | 108,970 | 7 | `2026-09-03` | EXACT |
  | **30 d** | 2026-08-25 | 200 | 115,351 | 9 | `2026-08-25` | **EXACT** |
  | 31 d | 2026-08-24 | 200 | 114,505 | 9 | `2026-09-23`, `2026-09-24` | **CLAMPED** |
  | 35 d | 2026-08-20 | 200 | 114,505 | 9 | `2026-09-23`, `2026-09-24` | CLAMPED |
  | 44 d | 2026-08-11 | 200 | 114,505 | 9 | `2026-09-23`, `2026-09-24` | CLAMPED |

  → **Days 0–30 return the requested day's own snapshot; day 31 and beyond silently
  return the current on-sale page.** Every clamped response was byte-identical to the
  current page (sha `5a897a517e8d…`).

- **Corrected silent-fallback rule (two false positives removed).**
  1. A **future** requested date is legitimately clamped *up* to the newest open sale
     day: `?date=2026-09-25` returned bytes identical to `?date=2026-09-24`. So
     HTTP 200 + identical bytes is **not** automatically a failure.
  2. `data-processdate` on the current page spans `{T−1, T}` (the sale window rolls
     over midnight), so the legacy rule "all `processdate == requested date`" flags
     today's perfectly valid page as `SILENT_FALLBACK_SUSPECTED`.
  The discriminator that does hold: for a **historical** request the requested date
  must appear in the payload's `data-processdate` set; for a **current or future**
  request, `processdate ⊆ {T−1, T, T+1}` is the whole condition.

### 4.3 BetExplorer homepage — the reference leg (`reference_proxy`)

`https://www.betexplorer.com/`

- Source type: **aggregator**. Label `reference_proxy`. It is **not** Pinnacle,
  **not** Betfair, and no named sharp book is implied.
- Free, unauthenticated. Rate-limits aggressively: HTTP 429 observed on 2026-09-23
  18:xx and again on 2026-09-24 09:07–09:09, cleared by the following 09:05. A
  4-second politeness delay was used throughout.
- **Page-semantics split (important).** Two markup dialects exist:
  - Homepage rows carry `data-dt="dd,mm,yyyy,hh,mi"` (minute-precise kickoff) and
    `data-ts` (epoch). **Only this dialect supports timestamp precision.**
  - League fixture pages (`/football/<country>/<league>/fixtures/`) render the kickoff
    as prose (`<td class="table-main__datetime">Today 02:30</td>`) and carry **no**
    `data-dt` at all. They can supply odds but not a machine-readable kickoff, so they
    were **not** used for the paired leg.
  - `results` pages were not used (§C: they are not valid for the live-reference leg).
  - Kickoff is UK time (BST = UTC+1) → Beijing = UK + 7 h. Verified: Seattle–Real Salt
    Lake `data-dt="24,9,2026,02,30"` ↔ official `matchTime = 09:30:00` Beijing.
- No provider update timestamp is exposed anywhere on the page.
- Payload shape: 119 dated rows, 106 with a complete 1X2 triple, **87 unique fixtures**
  after collapsing duplicates (each fixture is rendered twice, desktop + mobile).
- **Source-quality caveats, measured and disclosed:**
  - Of 19 fixtures rendered twice, **1 disagrees with itself inside the same payload**:
    Cameroon–Comoros appears as `1.33/4.30/8.82` and `1.33/4.31/8.84`. Reproducible in
    both rounds. Deduplication keeps the first copy; the affected fixture is not one of
    the paired rows.
  - The same URL serves **two payload variants** (582,627 B, sha `565c29cf…` and
    582,907 B, sha `7b760a60…`). Request headers were ruled out as the cause: a request
    with `Accept-Language` produced the 582,627 variant at 09:14:59 while the collector
    (no `Accept-Language`) produced 582,907 at 09:18:49. Of 8 comparable fixtures,
    **6 prices are identical and 2 differ by 0.01–0.11 on the away leg**
    (Japan–Uruguay 4.18 vs 4.19; Portugal–Wales 14.24 vs 14.13).
  - Consequence: cross-variant price comparison of `reference_proxy` is only valid
    within one variant, and a single snapshot carries ±0.11 rounding-scale noise.

## 7. Result and what remains unresolved

**Result: `SMOKE CAPTURED / D01 TIMING PRECISION STILL UNRESOLVED`**

- The Sporttery leg is captured from the **official** source with provider timestamps at
  two levels (per pool and per payload) *and* our `observed_at`.
- The reference leg is captured in the same window with our `observed_at` only.
  **BetExplorer exposes no provider update timestamp**, so the reference side cannot be
  placed on the provider's clock. A lead/lag test (D01-B) needs that: with only our
  observation times, a stale-price window cannot be distinguished from a difference in
  when each provider last moved. Hence the required `D01 TIMING PRECISION STILL
  UNRESOLVED` qualifier — stated rather than promoted into a completed timing test.
- The reference leg is a **proxy, not a sharp book**. Every figure for it carries that
  label. Nothing here substitutes closing odds, daily opens or a soft-book average for a
  sharp quote, and no timestamp was invented or interpolated.

### Reviewer ruling requested (safety boundary)

Flagged rather than self-certified. The route that unblocks the official endpoint works
by sending a `Referer` header whose value is the site's own public page URL. No
credential, token, cookie, account, IP rotation, proxy/VPN change or Cloudflare Workers
deployment was used, and no access control was otherwise circumvented.

**However, the Reviewer should rule explicitly on whether satisfying this WAF check by
sending `Referer` sits inside the task's "do not bypass access controls" line or outside
it.** If it is judged outside, the fallback is the 500.com mirror
(`sporttery_mirror_500`), which reproduces the official HAD prices exactly but does not
carry TTG on its default page and has no official update timestamp. The capture is
reproducible either way; only the primary leg changes. This was not resolved
unilaterally.

## 11. Second-review correction — F1 / F2 and report errata (2026-09-24)

`REVIEWS/TASK-0004.md` (2026-09-24 second review) rejected the v2 submission for a
narrow **implementation** reason while confirming the research result itself passes:

> `SMOKE CAPTURED / D01 TIMING PRECISION STILL UNRESOLVED` — **passes**.

Two BLOCKING findings were raised against the committed parser, and errata were
required. This section records the correction. **No external re-capture was
performed**: the stored raw payloads under `data/raw/p0_dual_market_smoke/` were
sufficient, exactly as the review anticipated ("Do not start TASK-0005 and do not redo
external collection unless the stored raw payloads are insufficient").

### 11.1 F1 — per-pool provider timestamps were collapsed (BLOCKING, fixed)

The v2 `SportteryQuote` exposed a single `odds_updated_at` equal to the **maximum** of
the HAD / HHAD / TTG stamps. On the captured `周三003 西雅图 vs 盐湖城` the five pools
carry **five different** provider stamps — HAD `18:51:22`, HHAD `18:51:31`,
CRS `20:06:47`, HAFU `21:38:47`, TTG `21:50:41` — so a single maximum would date a HAD
quote with TTG's clock, moving the measured stale interval by **2h59m19s**.

Fix applied in `src/football_betting/data/sporttery_webapi.py`:

- `odds_updated_at` **removed**.
- `pool_updated_at: Mapping[str, datetime | None]` added — one entry per pool code,
  `None` when that pool carries no stamp (absent stays absent, never back-filled).
- `latest_pool_updated_at: datetime | None` added as an **explicitly named aggregate**
  (the maximum), so it cannot be misread as any particular market's update time.
- Regression test `test_per_pool_provider_times_survive_separately` asserts the five
  stamps survive as five distinct values and that `ttg − had` is exactly `2h59m19s`.

### 11.2 F2 — per-pool executability fields were omitted (BLOCKING, fixed)

`poolList` carries `poolCode` / `bettingSingle` / `bettingAllup` / `poolStatus` /
`poolCloseDate` / `poolCloseTime`, and the v2 quote dropped them. D01-B asks whether a
stale quote is **still executable** — price + timestamp cannot answer that.

Fix: new frozen dataclass `PoolAvailability`, exposed on the quote as
`pool_availability: Mapping[str, PoolAvailability]` (keyed by lower-cased pool code).
Empty provider strings parse to `None`; a payload with no `poolList` yields `{}` rather
than a default of "sellable". Regression tests
`test_per_pool_availability_is_retained` (one match: HAD/HHAD `bettingSingle=0` vs
TTG/CRS/HAFU `bettingSingle=1`) and `test_absent_pool_list_stays_absent`.

### 11.3 Report errata (reviewer-required, non-blocking)

**E1 — 500.com hidden `bet-tb-end` rows.** The mirror's HTML can retain rows marked
`bet-tb-end` (visually hidden / concluded). Presence of a row in the mirror HTML must
**not** be treated as authoritative executability evidence. This does not change the
§5.3 result: the 16/16 `MATCH_EXACT` pairs were joined on `场次号` against the
*official* payload, not inferred from mirror-row presence.

**E2 — `matchNumStr` must be used in full.** `周三003` and `周四003` share the trailing
suffix `003`, so the suffix alone is **not** a unique key. Every join and record must
key on the complete string (e.g. `周三003`). The v2 smoke rows already carried the full
string; this is recorded as a forward rule for future parsers.

**E3 — mixed-encoding regions in the 500.com page.** The page is not decodable by a
single codec: it declares `gb2312`, is body-GBK, and embeds one UTF-8 JavaScript object
(`id="jsonggtype"`) at byte **77,510** — `utf-8` fails at byte 61, `gbk` at 77,510,
`gb2312` at 77,495. Decoding with `utf-8, errors="ignore"` silently drops every Chinese
character **without raising** (e.g. `data-matchnum="周三003"` becomes `"003"`), so a
silent-corruption path exists. Future parsing must detect the encoding region rather
than ignore errors. The v2 smoke rows are **not** invalidated — they were independently
rechecked — but any new 500.com parser must avoid this path.

**E4 — round spacing.** The two complete official/reference rounds in §5.1 were
**31 seconds** apart, not "a few minutes". §5.1's "as §F.4 requires" overstates this; it
is recorded here as a process miss. The reviewer confirmed it does not invalidate the
feasibility smoke and **no recapture was required for spacing alone**, so none was done.
