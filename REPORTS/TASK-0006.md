### 11.4 🚨 Disclosure of finding S1 — sealed logging leaked confirmation activity

**The run does not satisfy the strict sealed logging contract as written, and
this report does not claim that it does.**

TASK-0006 §5.5 forbids ordinary logs from revealing confirmation-trigger
activity. The sealed log
`/home/ubuntu/evlab-data/task0006-sealed-20260928a/logs/service.log` contains
repeated lines of the form:

```text
sporttery change_confirmation: capture ok
```

Independent count performed at closure: **456 such lines.** This matches the
`change_confirmation` capture count in the ledger exactly (456), which
cross-confirms that every confirmation produced one leaked log line.

Scope of the defect, checked independently at closure:

| Check | Result |
|---|---|
| `change_confirmation` occurrences in `service.log` | **456** |
| Lines matching odds / stale / handicap / settle patterns | **0** |

So the leak is **confirmation activity only**. No odds values, event
identities, stale-window conclusions or market results were exposed. That
narrows the defect; it does not excuse it, because confirmation activity was
explicitly prohibited on its own.

Root cause (Reviewer's finding, not re-litigated here): the frozen collector
contains

```python
LOGGER.info("sporttery %s: capture ok", kind)
```

inside the sealed branch of `_capture_sporttery()`. The round-level summary
correctly suppresses confirmation information, but this lower-level line
bypasses that protection.

Why the pre-run tests missed it: the frozen suite asserts sealed logs do not
contain `confirmation`, but exercises a round that never creates a real
accepted change/confirmation path. This is a **test-coverage defect**, not a
cloud-version mismatch — the full 263-test suite passes while the real path
still leaks.

**Not remediated in this run, deliberately.** The leaked lines were not
rewritten or deleted, and no post-run code change was applied to the frozen
checkout, because doing either would destroy the evidence of the defect or
contaminate the frozen run. The fix belongs to a separate follow-up task.
