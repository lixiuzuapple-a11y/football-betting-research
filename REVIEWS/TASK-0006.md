## 3. Blocking finding S1 — sealed log leaks confirmation activity

TASK-0006 §5.5 explicitly forbids ordinary logs from revealing:

- odds values;
- event-level change identities;
- change counts;
- confirmation-trigger activity;
- inferred stale-window/result information.

Independent audit of:

`/home/ubuntu/evlab-data/task0006-sealed-20260928a/logs/service.log`

found repeated lines of the form:

`sporttery change_confirmation: capture ok`

This is a real results-proxy channel: an observer can infer that an accepted reference change caused a confirmation capture at that timestamp.

No odds values, event IDs, stale-window conclusions, or specific market values were exposed by the inspected lines. Nevertheless, confirmation activity itself was explicitly prohibited.

The exact aggregate count is intentionally not repeated in this review narrative; the point is protocol compliance, not opening the sealed outcome distribution before an analysis plan is authorized.

### Root cause

The frozen collector contains:

`LOGGER.info("sporttery %s: capture ok", kind)`

inside the sealed branch of `_capture_sporttery()`.

When `kind == "change_confirmation"`, the supposedly operational-only log therefore reveals the confirmation.

The higher-level round summary correctly suppresses confirmation information, but the lower-level capture log bypasses that protection.

### Why the pre-run tests missed it

The frozen suite contains a test asserting that sealed logs do not contain `confirmation`, but that test exercises a round without creating a real accepted change/confirmation path.

Therefore all 263 tests can pass while the real confirmation path still leaks.

Reviewer independently reran the full local suite after the run:

This is a test-coverage defect, not a cloud-version mismatch.
