## 2. BLOCKING F1 — reference change interval upper bound is wrong

Severity: **HIGH / BLOCKING**

`ProspectiveCollector._capture_betexplorer()` correctly has the current BetExplorer
`outcome.response_received_at`.

However, in `run_round()`, when persisting a reference change, the implementation uses:

`current_response_received_at=datetime.now(timezone.utc)`

**after** the Sporttery confirmation fetch has already completed.

This is not the timestamp the reference quote became knowable. The required upper bound is the exact BetExplorer response-receive time from the current reference capture.

The error gets materially worse when many events change in one BetExplorer response because confirmations are currently executed sequentially. Later change rows can receive upper bounds seconds after the same BetExplorer response.

Required correction:

- carry the current BetExplorer `response_received_at` together with each detected change;
- write that exact timestamp as `current_response_received_at` / `change_interval_upper`;
- never substitute a post-confirmation `datetime.now()`;
- add a regression test proving a delayed confirmation cannot move the reference change interval.

## 3. BLOCKING F2 — canonical parse path silently replaces invalid bytes

Severity: **HIGH / BLOCKING**

`ProspectiveCollector._fetch()` currently does:

`raw.decode("utf-8", "replace")`

for the canonical parse text.

This directly conflicts with the repository data policy adopted after the 500.com finding:

- raw bytes are authoritative;
- research-critical parsing must not use permissive `errors='ignore'` or
  `errors='replace'`;
- decode ambiguity/failure must fail closed and remain visible.

Raw bytes and hashes are preserved, which is good, but silently replacing bytes before parsing can still corrupt identity/odds text while producing a seemingly valid parse.

Required correction:

- strict decode for sources whose contract is UTF-8;
- on decode failure, preserve raw/hash and record an explicit decode/parser failure;
- do not produce normalized facts from a payload that failed canonical decoding;
- add a deterministic invalid-byte regression test.

## 4. BLOCKING F3 — BetExplorer reference series is not stable enough for D01-B

Severity: **HIGH / BLOCKING FOR TASK-0006**

The qualification run itself correctly surfaced this, and Reviewer independently confirmed the problem has continued.

At the time of independent cloud inspection:

- captures: **2816**;
- regular BetExplorer captures: **439**;
- reference-change rows: **1938**;
- distinct changed event IDs: **106**;
- many events repeatedly occupy multiple recurring 1X2 tuples;
- the live log showed one regular round reporting **32 changes** followed by a burst of 32 Sporttery confirmation fetches.

This is not acceptable as a formal “reference market moved” signal.

Legacy evidence already warned that BetExplorer odds presentation can depend on page/cookie/provider-selection semantics. The current implementation chooses the first priced copy in document order and treats any cross-round tuple difference as a market movement. The qualification evidence demonstrates that this produces a large source-variant component.

Required correction:

1. diagnose the variant discriminator using existing raw captures first;
2. establish one stable, documented reference-series rule;
3. do **not** average variants, tune a movement threshold, or simply suppress small moves;
4. do **not** label a variant transition as a market move;
5. add regression fixtures representing the observed variants;
6. rerun a bounded qualification showing that stable unchanged pages no longer generate alternating false changes.

A bounded public re-probe is allowed only if stored raw captures are insufficient to determine the source semantics. Existing access redlines remain unchanged.

## 5. BLOCKING F4 — one reference response can trigger a confirmation request storm

Severity: **MEDIUM/HIGH / BLOCKING FOR FORMAL PILOT**

The current implementation performs one extra Sporttery fetch **per changed event**.

That is unnecessarily expensive and damages timing comparability when many events change in the same BetExplorer response. A single official Sporttery snapshot taken immediately after one BetExplorer response can confirm all changed fixtures from that response.

Reviewer correction to the TASK-0005 interpretation:

> **Use at most one Sporttery `change_confirmation` capture per successful BetExplorer capture/round that contains one or more accepted reference changes.**

All change rows from that reference capture should link to the same confirmation capture ID.

Required tests:

- 0 changed events -> 0 confirmation fetches;
- 1 changed event -> 1 confirmation fetch;
- N changed events in one reference capture -> still exactly 1 confirmation fetch;
- all N change rows link to that same confirmation capture.

## 6. F5 — round identity is reused across process restarts

Severity: **MEDIUM / MUST FIX BEFORE TASK-0006**

Reviewer independently reproduced duplicate regular-round IDs in the live ledger:

- `r00001`, `r00002`, `r00003` currently each occur three times;
- many later IDs occur twice.

`capture_id` remains unique, so qualification data integrity is not destroyed. But `round_id` cannot be used as a stable global round identifier, which is unsafe for a sealed prospective dataset.

Required correction:

- make the round identifier globally unique across process restarts, e.g. run/session UUID + monotonic round number, or another deterministic unique scheme;
- preserve human-readable sequence if useful, but do not reuse the primary round identity;
- add restart regression coverage.
